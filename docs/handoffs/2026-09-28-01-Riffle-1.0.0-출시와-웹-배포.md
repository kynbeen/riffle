# Riffle 1.0.0 출시와 웹 배포

**날짜:** 2026-09-28
**기기:** LAPTOP
**관련 명세:** 없음(배포 작업 — 백로그 「Riffle 1.0 배포」)

## 현재 상태

Riffle 1.0.0 을 냈다. 태그 `v1.0.0`(커밋 `45a576b`), GitHub Release 에 `Riffle-Setup-1.0.0.exe`, 웹은 Render 작업공간 `riffle` 의
서비스 `useriffle` — <https://useriffle.onrender.com> 이 `/api/health` 에 `"version":"1.0.0"` 으로 답하고 첫 화면 200. 실사용 확인
(태블릿·실제 강의)은 사용자 결정으로 건너뛰고 냈고 백로그에 열린 채 남아 있다. 남은 것은 옛 서비스 `riffle-9rnx` 삭제와 UptimeRobot
등록(둘 다 사용자 쪽) 정도다. 작업 트리 깨끗, `main` 푸시 완료, CI 초록.

## 이번 세션에 한 일

- **배포 가능 여부 점검** → 코드 결함 없음. 대신 `main` CI 가 빨간 상태였다: `tests/test_app.py` 가 CI 의 짧은 경로(`RUNNER~1`)를
  긴 경로와 비교해 실패, `test.yml` 이 지운 옛 화면 `riffle/static/app.js` 를 검사. 둘 다 고침(`85e9574`).
- **태그 체계:** 모든 제품 공통 원칙(`kynbeen/workspace` `docs/principles/제품-이름과-버전.md`)대로 `vMAJOR.MINOR.PATCH`.
  NotEditor 태그를 `noteditor-v1.0.0`~`-v1.2.0` 으로 복사해 올리고, GitHub 릴리스 셋을 그 태그로 옮겨 「NotEditor 1.x」로 이름 바꿈.
  옛 `v1.0.0`~`v1.2.0` 삭제는 자동 승인에 막혀 **사용자가 직접** 지웠다. `riffle/version.py` 의 `git describe` 에 `--match "v[0-9]*"`.
  사용자가 미뤄 둔 세 파일(개발 체크아웃은 남은 `_version.py` 보다 git 을 먼저 봄)도 같이 커밋.
- **웹은 릴리스 때만 배포:** Render 서비스가 `release` 가지를 따르고, `release.yml` 의 `web` 작업이 `v*` 태그 때 태그 커밋 +
  버전 파일(`riffle/_version.py`, 강제 추가) 한 커밋을 `release` 로 강제 푸시한다. 릴리스 이름은 다음부터 「Riffle <버전>」(`e0c138c`).
- **Render:** Render CLI 설치(`C:\Users\ruxxl\bin\render.exe`, v2.28.0), `render login`(사용자 브라우저 승인 한 번).
  사용자가 2026-09-26 만든 `riffle-9rnx`(작업공간 NotEditor)가 `main` 을 배포하고 있어 `release` 가지로 돌렸다.
  `riffle.onrender.com` 요청 → 두 번 만들어 두 번 다 접미사(`riffle-9rnx`, `riffle-bcp6`) = 다른 계정이 잡고 있음. `riffle-bcp6` 은 지움.
  사용자가 `useriffle` 을 골라 작업공간 `riffle` 에 만들었다(`srv-dasj0q8473hc738h6ib0`).
- **첫 배포 실패와 복구:** Git Bash 가 `--health-check-path /api/health` 를 `/Program Files/Git/api/health` 로 바꿔 넣어 헬스 체크가
  404 → 시간 초과. `MSYS_NO_PATHCONV=1` 로 경로를 고치고, 옛 설정을 든 배포를 취소 후 `e35a63d`(release) 재배포 → 성공.
- **문서:** README(웹 주소·배포 구조·태그 전 할 일·Sleek 엔진 입구), 설치 안내(「설치 없이 웹으로 쓰기」 새 절, 걷은 Android 빌드 절 삭제),
  현재 상태(기준일·버전·시험 수), 백로그(배포 항목 닫음).
- **모든 프로젝트 공통 규칙:** workspace 원칙 문서에 「새 태그 전에 할 일」 절(`db1db92`), 개인 설정 0.2.1 에 "태그 전에 그 절을 따른다"
  (`plait-personal` `f3b8f88`), 이 PC 의 Claude Code·Codex·Antigravity 설치본 갱신.

## 내린 결정과 근거

- **옛 태그를 `noteditor-v*` 로 옮기고 Riffle 이 `v*` 를 쓴다** — 사용자가 "공통 넘버링 규칙 적용"을 지시. Plait 도 `v1.0.0` 형식.
  이전 계획 `riffle-v*` 는 폐기.
- **웹은 `release` 가지로만 배포** — 공통 원칙 "개발 중 커밋을 완성된 제품 버전으로 표시하거나 자동 배포하지 않는다". 도커 이미지엔 깃이
  없어 버전을 알 수 없으니 버전 파일을 그 가지에만 얹는다(시크릿·API 키 없이 되는 방식).
- **문서만 고쳐 `main` 에 올려도 웹은 다시 배포되지 않는다** — Render 는 `main` 을 보지 않는다. 배포는 `v*` 태그 때만. (사용자 질문
  "문서 업데이트시 deploy 안 되게 못 해?"의 답 — 이미 그렇게 돼 있다. 이번 세션 배포는 서비스 생성 때의 첫 배포와 `v1.0.0` 태그 둘뿐.)
- **UptimeRobot 대상은 `/api/health`** — 가볍고 작업공간(접속자별 임시 폴더)을 만들지 않는다(2026-08-28 결정 그대로).

## 고려했다가 안 한 것

| 대안 | 왜 안 했나 |
|---|---|
| `riffle-v*` 태그 | 공통 원칙과 다름 — 사용자가 공통 규칙 적용을 지시 |
| `riffle.onrender.com` | 다른 계정이 잡고 있다(두 번 만들어 확인). 이미 만든 서비스의 주소는 바꿀 수 없다 |
| Netlify·Vercel·Cloudflare Pages | `riffle.` 주소가 이미 쓰이고, 서버리스라 세션·100MB 업로드를 못 받는다. Fly.io·Railway 도 `riffle.` 선점 |
| 도메인 구입 후 연결 | 사용자가 `useriffle.onrender.com` 을 골랐다 |
| 웹 배포를 Render API 키 + 배포 훅으로 | GitHub 시크릿이 필요하고 사용자 개입이 늘어난다 — 가지 방식이면 필요 없다 |
| 태그 전 실사용 확인(태블릿 등) | 사용자 결정으로 건너뛰고 1.0.0 을 냈다 — 백로그에 열린 채 |

## 미해결 질문 / 블로커

- **옛 서비스 `riffle-9rnx`(작업공간 NotEditor, `srv-darkjsvavr4c73f2targ`) 삭제** — 자동 승인에 막힘. `release` 가지를 따르므로 두면
  릴리스 때마다 같이 배포되고 NotEditor 작업공간 무료 시간을 쓴다. 사용자가 대시보드에서 지우거나 "지워"라고 하면 `render services delete`.
- **UptimeRobot 모니터** — 사용자가 등록: HTTP(s), `https://useriffle.onrender.com/api/health`, 5분. 등록 뒤
  `render logs -r srv-dasj0q8473hc738h6ib0 --path /api/health` 로 5분마다 들어오는지 확인하고 README 「Docker 배포」에 한 줄 적는다. 미확인.
- 웹의 실제 환경 변수(`RIFFLE_MAX_UPLOAD_MB=100`, `RIFFLE_SESSION_TTL=3600`)는 만들 때 넘긴 값 — 서비스에서 다시 읽어 대조하지는 못함(조회가 막힘).
- 작업공간을 나눠 무료 시간을 늘리는 것은 Render 가 할당량 우회로 볼 여지가 있다(사용자에게 알림).
- 실사용 확인들(새 화면 단위 7, 검토 깊이 단위 5, Sleek 필기본 갱신 단위 7·8) — 열린 채.

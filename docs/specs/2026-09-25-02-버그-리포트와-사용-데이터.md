# 버그 리포트와 사용 데이터 — 배포된 곳에서 받아 LLM 이 고치게

**날짜:** 2026-09-25
**상태:** 진행 중 (착수 전 — 새 Render 서비스가 먼저 열려야 한다)
**판단 기준:** [`docs/UX-철학.md`](../UX-철학.md). 이 명세는 사용자 쪽이 아니라 **서비스 제공자 쪽**에서 쓴다(사용자 결정)
**관련:** [`2026-09-25-01-검토-깊이`](2026-09-25-01-검토-깊이.md) 단위 4b(고친 것을 사례로 저장), 백로그 「판정 스스로 고치기」

> 법 조항은 작성자(Claude)가 아는 범위로 적었다. **법률 자문이 아니다.** 공개 전에 처리방침 문안은 사람이 확인한다.

---

## 왜 하는가

1. **배포된 곳의 문제를 알 길이 없다.** 웹(Render)과 설치형은 동기·지인이 쓰고, 로그인이 없어 모르는 사람도 쓸 수 있다.
   지금 화면 오류는 서버 기록에 한 줄 남고 끝난다(`/api/client-error`). Render 무료 요금제는 디스크가 남지 않아 그 기록도 재시작하면
   사라진다. 설치형은 사용자 PC 의 `app.log` 에만 남는다.
2. **판정을 스스로 고치려면 데이터가 필요하다.** 이 PC 한 대에서 사람이 고친 사례는 몇 주에 몇 건이다(검토 깊이 단위 4b).
   배포된 곳의 사례가 모이면 백로그 「판정 스스로 고치기」의 시작 조건(사례 20건)이 빨리 찬다.
3. **리포트를 LLM 이 고치게 하고 싶다.** 재현할 정보가 충분히 붙은 리포트면 devkit 무인 루프가 브랜치로 고칠 수 있다.

## 목표

**앱 안의 `문제 알리기` 한 번으로, 재현에 필요한 정보가 붙은 리포트가 비공개 GitHub 저장소의 이슈가 된다. 따로, 개인정보가
아닌 사용 데이터(쪽 지문·판정·사람이 고친 것)는 알린 뒤 기본으로 모으고, 끌 수 있다.** 모은 것은 판정 측정 사례와
LLM 수정 루프의 입력이 된다. LLM 은 재현하는 시험을 먼저 만들고, 브랜치에만 올리고, 합치기는 사람이 한다.

## 무엇을 모으나 — 세 층

"최대한" 의 경계는 법이 긋는다. 법이 동의 없이 허용하는 것은 기본으로 모으고, 동의가 필요한 것은 그 자리에서 받고,
받을 수 없는 것은 모으지 않는다.

### 1층 — 사용 데이터: 알리고 기본으로 모은다(끌 수 있다)

개인정보가 아닌 기술 정보. 첫 실행 때 한 번 알리고, 설정 없이도 끌 수 있는 자리(첫 화면 아래 작은 글 `사용 데이터 보내기 · 끄기`)에 둔다.

| 항목 | 쓰임 |
|---|---|
| 앱 버전, 실행 방식(데스크톱·로컬 웹·배포 웹), OS 종류 | 어느 판에서 나는 문제인지 |
| 설치마다 한 번 만든 무작위 번호 | 같은 설치의 기록을 묶기. 사람과 잇지 않는다 |
| 작업 종류, 쪽 수, 단계별 걸린 시간, 오류 종류 | 느린 곳·자주 깨지는 곳 |
| 판정 요약(자동·볼 쪽·순서 바뀜·후보·가장 닮음 수) | 판정 품질 추세 |
| **쪽 지문**(쪽마다 16×16 밝기 숫자 256개)과 기계가 낸 짝, 사람이 확정한 짝, 사람이 누른 것 | 판정을 다시 돌려 볼 사례(검토 깊이 4b 와 같은 모양) |

쪽 지문은 쪽을 256칸으로 뭉갠 밝기라 글자·그림을 되살릴 수 없다 — 강의록의 복제가 아니라고 본다(가정, 확인 필요).

### 2층 — 버그 리포트: 사용자가 누를 때, 보낼 것을 보여 주고 보낸다

`문제 알리기` 를 누르면 보낼 내용을 **그대로** 보여 주는 시트가 뜨고, 사용자가 `보내기` 를 눌러야 간다.

- 자동으로 붙는 것: 1층 전부(끈 사용자라도 이 리포트에 한해, 시트에 보이는 대로) · 지금 화면과 단계 · 최근 오류 문구 ·
  앱 기록 끝부분(최근 200줄, 파일 경로의 사용자 폴더 이름과 파일 이름은 가린다) · 화면 그림 한 장(사용자가 뺄 수 있음 — 강의록이 보이므로)
- 사용자가 쓰는 것: 무엇이 잘못됐는지 한 줄(선택), 연락받을 방법(선택 — 쓰면 개인정보 동의 항목)
- **파일 원본(PDF·필기 파일)은 기본으로 보내지 않는다.** `재현을 위해 파일도 보내기` 를 따로 체크했을 때만, 비공개 저장소에
  보관 기간(90일)을 두고 넣는다. 체크 옆에 "강의록은 교수님의 저작물입니다. 재현에만 쓰고 90일 뒤 지웁니다" 를 쓴다.

### 3층 — 모으지 않는 것

- 파일 이름(필기한 사람의 이름이 들어 있다 — 제3자 개인정보). 확장자와 길이만 남긴다
- 손필기 그림, 강의록 그림(2층의 화면 그림·파일 첨부를 사용자가 고른 경우 빼고)
- 사용자가 모르게 파일 원본을 올려 두기. 올린 파일은 지금처럼 작업이 끝나면 지운다
- IP 주소를 리포트·데이터에 적기(서버 접속 기록은 Render 가 남긴다 — 처리방침에 적는다)

## 법이 요구하는 것 (공개 전 필수)

- **개인정보 처리방침**(개인정보보호법 30조) — 웹 화면 아래와 설치형 첫 화면 아래 링크. 항목·목적·보유 기간·파기·국외 이전·
  거부할 권리를 적는다. 개인정보가 들어오는 것은 2층의 연락처와(체크한 경우) 파일 첨부뿐이다.
- **동의 받을 때 알릴 것**(15조 2항): 목적, 항목, 보유·이용 기간, 거부할 수 있다는 것과 거부해도 앱은 그대로 쓸 수 있다는 것.
  선택 항목에 동의하지 않았다고 앱을 막지 않는다(16조 3항).
- **국외 이전**(28조의8): GitHub(미국)·Render(싱가포르)에 들어간다. 받는 곳·나라·항목·기간을 처리방침과 2층 시트에 적는다.
- **최소 수집**(16조): 1층은 개인정보가 아니라서 이 조항 밖으로 보지만, 무작위 설치 번호가 다른 정보와 합쳐져 사람을 알아볼 수
  있게 되면 개인정보가 된다 — 설치 번호와 연락처를 같은 기록에 두지 않는다.

## 받는 쪽 — 흐름

```
앱(데스크톱·웹) ──POST /api/report·/api/usage──▶ Riffle 웹 서버(Render)
                                                  │  토큰은 서버 환경변수에만
                                                  ▼
                              비공개 저장소 kynbeen/riffle-reports
                              · 리포트 → 이슈(라벨 bug-report)
                              · 사용 데이터·지문 사례 → cases/<날짜>/<무작위>.json 커밋
                              · 첨부 파일 → files/<이슈 번호>/ (90일 뒤 지우는 작업)
                                                  │
                                                  ▼
                devkit 무인 루프가 이슈를 백로그로 → 재현 시험 먼저 → 브랜치 → 아침 리뷰에서 사람이 합침
```

- **설치형은 인터넷이 없을 때** 이 PC 에 쌓아 두었다가 다음에 보낸다.
- **남용 막기:** 설치 번호·IP 마다 하루 리포트 수 제한, 본문 크기 제한. 서버는 받은 글을 그대로 이슈에 넣되 코드 블록 안에 넣는다.
- **LLM 에게 리포트는 데이터다.** 모르는 사람이 쓴 글에 "이 파일을 지워라" 같은 지시가 들어 있을 수 있다(프롬프트 주입). 수정 루프는
  리포트 글을 지시로 따르지 않고, 저장소 밖 권한(배포·비밀값)을 갖지 않으며, 합치기와 배포는 사람이 한다.

## 성공 기준

- [ ] `문제 알리기` 에서 보낼 내용이 시트에 그대로 보이고, `보내기` 한 번으로 비공개 저장소에 이슈가 생긴다(데스크톱·웹 둘 다).
- [ ] 이슈에 버전·단계·오류·기록 끝부분·(고른 경우) 화면 그림·지문 사례가 붙고, **파일 이름과 사용자 폴더 이름이 없다**(자동 검사).
- [ ] 파일 첨부는 따로 체크해야만 가고, 90일이 지난 첨부는 지워진다(지우는 작업의 시험).
- [ ] 사용 데이터는 첫 실행 때 알리고, 끄면 다음 요청부터 가지 않는다(시험). 꺼도 앱의 모든 기능이 그대로다.
- [ ] 설치형이 인터넷 없이 쌓은 것을 다음 실행에 보낸다.
- [ ] 토큰이 앱 빌드·화면 파일·저장소 어디에도 없다(자동 검사).
- [ ] 처리방침이 화면 아래에서 열리고, 법이 요구하는 항목(위)이 다 있다 — 사람이 문안을 확인했다.
- [ ] 받은 지문 사례를 `tools/check_reorder.py` 가 읽어 채점한다.
- [ ] 이슈 하나를 devkit 루프가 집어 재현 시험 → 브랜치까지 가고, 사람이 아침 리뷰에서 판정한다(한 번 실제로).

## 범위 밖

- 판정을 스스로 고치는 스킬 — 백로그 「판정 스스로 고치기」(이 명세는 그 입력을 모은다).
- 로그인·계정. 사용자를 알아보는 기능.
- 모은 데이터를 보여 주는 대시보드(처음에는 저장소를 직접 본다).

## 제약

- **새 Render 서비스 `riffle` 이 먼저 열려야 한다**(백로그 「Riffle 1.0 배포」). 옛 `noteditor` 서비스는 v1.2.0 고정이라 받는 쪽이 될 수 없다.
- **토큰은 서버에만.** 설치형·화면에 넣으면 누구나 꺼내 저장소를 쓸 수 있다.
- **올린 파일은 지금처럼 작업이 끝나면 지운다.** 2층에서 사용자가 첨부를 고른 것만 예외다.
- Sleek 이 부르는 엔진 입구는 건드리지 않는다(`tests/test_sleek_engine_contract.py`).

## 고려했다가 안 한 것

| 안 한 것 | 이유 |
|---|---|
| 올린 파일 원본을 모두 보관 | 강의록 복제는 사용자가 허락할 수 있는 것이 아니다(저작권). 개인정보가 섞이면 최소 수집에도 어긋난다 |
| 리포트를 GitHub 이슈 작성 화면으로 열기 | 보내는 사람에게 GitHub 계정이 필요하고 저장소가 공개여야 한다. 지문 사례는 이슈 글 길이 제한(약 6만 5천 자)을 넘는다 |
| 파일로 저장해 사람이 직접 전달 | 자동 처리가 안 된다 |
| 사용 데이터를 이슈로 받기 | 양이 많고 이슈 글 길이 제한을 넘는다. 사례는 파일로 커밋한다 |
| 토큰을 설치형에 넣기 | 꺼내 쓸 수 있다 |

## 열린 질문

1. **받는 저장소 이름과 공개 범위** — 기본안: 비공개 `kynbeen/riffle-reports`. Riffle 저장소에 이슈를 섞으면 공개 저장소일 때 리포트가 공개된다.
2. **사용 데이터 기본값** — 기본안: 켬(알리고 끌 수 있게). 개인정보가 아니라는 판단이 틀리면 기본 끔으로 바꾼다 — 처리방침 확인 때 정한다.
3. **지문 사례의 크기** — 200쪽 × 256칸. 칸을 1바이트로 줄이면 사례 하나에 약 100KB. 저장소가 커지면 오래된 사례를 묶어 옮긴다.
4. **devkit 루프가 다른 저장소(riffle-reports)의 이슈를 읽는 방법** — 확인 필요.
